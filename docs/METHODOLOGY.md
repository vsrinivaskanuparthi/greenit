# Methodology and limitations

## Scientific boundary

Source code cannot establish actual emissions. Static optimisation findings, supplied resource/energy measurements and modelled carbon estimates are kept separate. Source-only scans show **“Carbon estimate unavailable — measurement inputs required.”** Repository size, ZIP size, lines of code, finding counts, execution time and CPU utilisation are never treated as measured energy. There is no green score, sustainability certification or guaranteed carbon saving. Zero findings can mean no recognised pattern or no applicable coverage.

## Static rules (v1.0.0)

All six rules use Babel AST structure, not regex-only semantic detection. Severity is medium (review-worthy, not a quantified energy impact). Confidence describes pattern recognition, not confidence in savings.

| Rule | Trigger | Scope / important exclusions |
| --- | --- | --- |
| `await-fetch-in-loop` | Awaited unshadowed global `fetch` directly within a loop | High confidence; excludes calls in nested function bodies. Does not attempt arbitrary database/client API recognition. Dependencies, ordering and rate limits can justify sequential work. |
| `short-interval` | Unshadowed global `setInterval` with numeric literal delay from 0 to below 1000 ms | High confidence; a review threshold, not a scientific efficiency threshold. Dynamic expressions and intentional real-time workloads require judgment. |
| `sync-fs-handler` | Known synchronous `fs`/`node:fs` member call in an inline handler of an app created by an imported Express function | High confidence; ES imports and identifiable direct handlers only. Destructured fs calls, CommonJS handlers, wrappers and other frameworks are outside this heuristic. |
| `constant-json-in-loop` | `JSON.parse` of a constant string-literal binding declared outside the enclosing loop | High confidence; excludes mutable bindings and loop-local literals. Hoisting changes object identity and mutation isolation. |
| `effect-interval-cleanup` | React-imported effect callback creates a global interval with no matching handle cleared in a returned cleanup function | Medium confidence; helper cleanup/custom hooks and indirect return paths may be missed. It detects identifiable cleanup, not proof of cleanup on every control-flow path. |
| `request-reference-json` | UTF-8 fixed reference JSON read and parsed in an inline Express handler | High confidence; direct ES-imported fs only, external constant/literal paths, no dynamic/mutable paths or shadowed globals. See the Express experiment below. |

Each finding gives fixed, non-source evidence, explanation, suggested review, trade-offs and practical verification. No automatic rewrites. Narrow `fetch` and Express detection were chosen instead of broad network/database or request-handler guesses. Dependency and import evidence can detect Node/React; language evidence alone is not a complete framework inventory. Straightforward Angular/Java markers are labelled unsupported; generic JS patterns in an Angular repository do not constitute an Angular analyser. Java-only or empty scans show no applicable coverage.

Default traversal respects local ignore files; built-in exclusions cannot be reversed. Negation cannot re-include children of an already excluded directory. A scan selected within a repository applies ignore files from the selected root down, not ancestors outside it. Excluded directories are represented once, not as a census of every hidden file. Errors do not include source excerpts. Sequential file processing bounds concurrency; time checks occur between entries, while ZIP workers also have a hard process deadline. A changing local tree is not a reproducible snapshot; avoid editing source during a scan.

## Finding comparison

Fingerprint = SHA-256 of rule ID/version, relative file path, AST node with location/comment metadata removed, and occurrence index among identical nodes. This survives whitespace, comments and line shifts. File renames, rule upgrades and expression changes can appear as resolved plus added; identical repeated nodes cannot be distinguished semantically. Comparison is offered only for scans assigned to the same local project. Import provenance is self-reported and not independently verified.

## A. Operational carbon estimate

`gCO₂e = kWh × electricity intensity (gCO₂e/kWh)`. With a strictly positive completed-work count, divide by that count for gCO₂e per declared unit. Energy and carbon factor must be explicitly supplied as finite, nonnegative numbers; zero is accepted and missing values are rejected. Period, system boundary, workload description and input provenance are required. Work count and unit must be supplied together. The demo accepts work counts from 1e-9 to 1e15, and energy, intensity and byte values up to 1e15, preventing non-finite arithmetic results. Optional factor source/date/region are retained.

This estimates operational electricity-related emissions within the declared boundary. It excludes embodied hardware and is not a complete SCI assessment. “Measured inputs” does not mean emissions were directly measured, nor that this application verified those inputs. Synthetic inputs are labelled illustrative and have no demonstrated causal connection to source edits.

## B. CO2.js transfer estimate

Pinned package **`@tgwf/co2@0.18.0`**, explicitly constructed as `new co2({model: 'swd', version: 4})`; call `perByte(bytes, greenHosting)`. The package/model API was checked against official [model documentation](https://developers.thegreenwebfoundation.org/co2js/models/overview/) and [perByte documentation](https://developers.thegreenwebfoundation.org/co2js/functions/perbyte/) on 2026-10-02. Package lock and saved model/version fields support reproducibility.

SWD v4 uses transferred data as a proxy to model datacentre, network and user-device use and embodied emissions. Library default factors and assumptions are used. Bytes must be explicitly supplied application traffic; archive size is never used. Green hosting is an explicit user assumption, false by default; there is no hosting lookup. The whole calculation runs locally. A supplied measured byte count still produces a modelled carbon result, not measured energy. See the official documentation for the underlying model; repository documentation does not substitute for it.

The two calculators have different, potentially overlapping boundaries. **Never sum them.** No uncertainty intervals, annual projections or causal savings are inferred. Carbon comparison requires identical declared period basis, boundary, workload, completed-work count and unit, provenance, and (for CO2.js) package/model version and hosting assumption. Equality is a conservative eligibility check, not independent scientific verification. Operational inputs can use different intensity factors; any resulting difference includes that factor change and must not be attributed solely to code.

## Synthetic values

`examples/synthetic-measurements.json` supplies an invented 0.25 kWh and 400 gCO₂e/kWh, yielding 100 gCO₂e or 0.1 gCO₂e per 1,000-work-unit batch member. Separately, 100,000,000 bytes with SWD v4 and green hosting false yields 14.82 gCO₂e. Neither value is a measurement from the sample applications. There is no manufactured before/after energy reduction.

## Express reference-data experiment

This separate, versioned benchmark artifact (`express-benchmark/1.0`) combines **measured local resources**, **synthetic business data**, and an **illustrative operational energy scenario**. It is not an uploaded-source execution facility and is not a measurement of application emissions.

The plain JavaScript Express before handler reads and parses the same small reference JSON on every request. The after process loads it once at startup. Both send identical 790-byte JSON bodies. Restart each after process when the reference file changes; never mutate its shared cached object. Caching retains memory and can serve stale data until restart. The experiment does not assume a meaningful memory saving or universally beneficial cache.

The additional AST rule `request-reference-json` v1.0.0 recognises an unshadowed `JSON.parse` directly wrapping imported `fs.readFileSync` with UTF-8 encoding and a fixed JSON path, inside a directly identifiable inline Express request handler. Fixed paths may be a literal or an external constant, including `new URL(..., import.meta.url)`. Dynamic paths, mutable bindings, shadowed globals and startup parsing are excluded. This deliberately narrow heuristic does not resolve arbitrary middleware, helpers or CommonJS patterns. Its findings overlap with the existing synchronous-filesystem rule; neither finding quantifies emissions. The original five rules and report schema remain compatible.

### Controlled collection

`npm run benchmark:express` runs six repetitions per version, alternating before/after order by pair, with a fresh target process for every repetition. Each process receives 500 warm-up requests followed by 10,000 measured requests at concurrency 8, using HTTP/1.1 loopback keep-alive. Every response must have status 200, JSON content type and the exact expected JSON body; failures and invalid responses remain in the record. No favourable runs are selected. The generator and target are separate processes. The same Node binary, Express installation, data, configuration and machine are used for both versions. Target processes have a 120-second deadline.

The target brackets the measured batch with IPC begin/end messages. Wall duration includes small IPC overhead, socket handling and waiting on the local generator; it is not isolated handler latency. `process.cpuUsage()` differences are converted from microseconds to milliseconds. They cover the whole target process, including V8/runtime work, and may exceed wall time due to runtime threads. They are **not energy**. The generator's CPU time is recorded separately. RSS/heap snapshots are taken at the boundaries; RSS is also sampled every 50 ms, which can miss brief peaks. `resourceUsage().maxRSS` is separately labelled lifetime KiB (including startup/warm-up); it is not the measured-batch peak. HTTP body bytes exclude headers, TCP/IP overhead and retransmissions, so are payload bytes, not actual network bytes. See the [Node process API](https://nodejs.org/docs/latest-v22.x/api/process.html).

Startup, cache loading and warm-up are excluded from the timed batch and reported separately where applicable. Filesystem caches are not flushed: warm repeated reads can benefit from the OS cache. CPU scheduling, thermal state, frequency scaling, JIT/GC and other processes remain uncontrolled. Target and generator share the host; generator bottlenecks can influence duration. Run on an otherwise quiet machine. The saved environment identifies CPU, OS, Node/Express versions and memory, not private hostnames or workstation paths. Code/data hashes, configuration, all repetitions and raw measurements are saved. Means, ranges and population standard deviations describe these repetitions, not uncertainty intervals or universal causal effects.

### Energy choice and transparent scenario

On the inspected Apple M1/macOS machine, Linux powercap counters were unavailable and `powermetrics --samplers cpu_power -n 1 -i 1000` required superuser access. No privileged sampler was run. No suitable application energy measurement was available. The benchmark does not claim to detect or acquire energy on other machines; replacing the scenario with validated metering would require separate methodological work.

The locally bundled `examples/express-reference/scenario.json` supplies **hypothetical 10 W** of fixed operational compute allocation during the measured batch and **illustrative 400 gCO₂e/kWh** electricity intensity, dated 2026-10-02, region “Hypothetical supply”. Neither is a measured value, TDP conversion, calibrated M1 model, current grid factor or Airbus-specific input. Model `fixed-allocation-time` v1.0.0 deliberately illustrates a conditional calculation:

```
energy (kWh) = assumed allocation (W) × target elapsed (ms) / 3,600,000,000
operational carbon (gCO₂e) = energy (kWh) × intensity (gCO₂e/kWh)
carbon per 1,000 successful requests = operational carbon × 1,000 / successful requests
```

The dimensional operational formula follows the [Green Software Foundation SCI specification](https://sci.greensoftware.foundation/) (`O = E × I`); that source does **not** supply or endorse the illustrative 10 W or 400 factor. This is **not a complete SCI assessment**. CPU time is never converted to power or energy. The model assumes allocation ends when the batch ends; if infrastructure remains provisioned/idle, faster completion need not reduce electricity. Exclusions include storage/network energy, load-generator energy, cooling/PUE, embodied hardware, startup, warm-up and idle periods outside the batch. There is no whole-lifecycle claim. CO2.js estimates remain separate and must not be summed with it.

Dashboard estimates are recomputed from saved raw inputs, not hard-coded. Comparison requires complete paired runs, equal workload/concurrency/warm-up, environment, model, boundary, response hash and expected source versions, with zero measured or warm-up failures. Incompatible/failed runs suppress the difference and percentage. A zero baseline suppresses percentage; no successful requests means no per-task estimate. The sign follows actual results (“Lower estimate” / “Higher estimate”), never a promised reduction. Reruns may differ. Ordinary source reports never inherit this example's numbers.


### Browser orchestration and interpretation

The browser now starts this same benchmark automatically from a verified bundled sample, or from an exact ZIP content match. No carbon input is requested. The central versioned scenario parameters are unchanged. Worker stages record actual source verification, static checks, workload execution and calculation; an indeterminate indicator avoids invented progress percentages. All saved browser results preserve source and measurement provenance and remain separate from ordinary static reports.

The primary label is “Scenario CO₂e per 1,000 successful requests”, scoped immediately to “Express sample · standard test workload · operational compute”. An overlapping before/after range is called inconclusive relative to observed variability; arithmetic differences remain descriptive, with no significance or confidence-interval claim. Recommendations distinguish static potential, observed CPU/duration/memory differences and scenario carbon differences.

The animation is explicitly an illustration, not a trace: repeated file/parse work before, cached data reuse after. It has a full static text equivalent and respects pause/reduced-motion preferences. Numeric values never come from animation state. CO2.js is not applied automatically because collected bytes are local loopback HTTP bodies rather than traffic representing its internet web-delivery system boundary; inventing internet transport for those bytes would be misleading. Existing advanced calculators are unchanged and kept separate.

## EcoLens traffic-first revision (current primary workflow)

The EcoLens flow supersedes the compute-first journey above without reinterpreting historical results. Source analysis and traffic estimation are independent. Existing six rules remain; no unreliable inference of SQL rows, database-call frequency or payload sizes from names was added. The sample's list-field recommendation is supported by known source/route mapping and observed journey bytes, not a new generic rule. Same-line reference-JSON/synchronous-file findings are grouped visually; original findings remain in reports.

HAR 1.1/1.2 parsing follows the [HAR response definition](https://github.com/ahmadnassri/har-spec/blob/master/versions/1.2.md#response). Only integer `response.bodySize` in [0, 10¹²] is admitted. Missing/null/−1 is unknown; other negative/noninteger/oversize values are invalid. A positive body for HEAD/204/205/304 is inconsistent and excluded. Status 0/missing/invalid or explicit `_error` excludes network-failed records; 4xx/5xx known bodies remain included. Explicit `_fromCache` (true, or entry disk/memory), `_fromDiskCache`, `_fromMemoryCache` and `_fromServiceWorker` flags exclude cached/replayed entries rather than claiming their decoded content crossed a network. HAR cache metadata alone is not proof of a cache hit. Unknown extensions are not inferred. No `content.size`, text, `_transferSize`, session total or constituent/session double-counting is used. Exporters omitting bodySize have incomplete/no coverage, not zero emissions. A zero estimate requires at least one explicitly known zero-byte response.

`apps/api/src/traffic.ts` is the common server-side estimator for HAR and the sample, reusing `packages/shared/src/carbon.ts`. CO2.js 0.18.0 is explicitly constructed with SWD v4 and `perByte(bytes, false)`. Official [overview](https://developers.thegreenwebfoundation.org/co2js/overview/), [model](https://developers.thegreenwebfoundation.org/co2js/models/overview/), and [function](https://developers.thegreenwebfoundation.org/co2js/functions/perbyte/) documentation were inspected 2026-10-02. The installed SWD v4 constants are operational kWh/GB: datacentre .055, network .059, device .080; embodied: .012, .013, .081; global intensity 494 gCO₂e/kWh. Thus the pinned default is linear in bytes (decimal GB). Calculations invoke the library rather than reimplementing that formula. Inputs, assumptions, model/library version, constants, source/check date and full precision are stored. The global model factor is not a current Airbus/local factor. Ember attribution (CC BY-SA 4.0) follows the model documentation; no regional Electricity Maps data is selected. CO2.js code is Apache-2.0, by Green Web Foundation; SWD model attribution is Sustainable Web Design.

The catalogue journey reuses the owned target process with literal `catalog-before`/`catalog-after` selectors. Each starts a temporary seeded SQLite database and separate local mock HTTP listener. Three alternating repetitions per version each perform one unrecorded warm-up then seven sequential requests. The task reads all 12 list records across three pages and verifies every required field, full product detail, reference data, order lines/total and stock availability against fixtures. Measured response-body bytes include only client-facing responses (identity encoding); internal mock responses, headers, request data and warm-up are excluded. Per-journey before/after means and ranges preserve all runs; no favourable run is selected. Any failed status/body/task validation fails the job, preventing a misleading comparison. A localhost/intranet transfer is deliberately a declared SWD reference scenario, not measured local-network electricity. No compute scenario is added. Equal bytes produce equal estimates, including the reference-cache endpoint.

Generic HARs retain anonymous request ordinals instead of URLs. No generic endpoint/source mapping or per-line carbon attribution is guessed. The bundled source has an explicit known products-route mapping; its contribution remains endpoint/journey-level. Optional SVG/CSS arrows are illustrative, have static text, pause and reduced-motion support, and never supply numbers. UI rounds to three significant figures; exports retain full precision. This is not whole-production or lifecycle accounting for the submitted application.
